# UGS v0.2.0

**Release status:** baseline content closed; publication still requires a
signed annotated `v0.2.0` tag.

**Specification:** UGS Core v0.2
**Repository profile:** `continuous` / `rebase-ff`
**Version policy:** `semver`
**Signing level:** `high-trust-commits-signed`

## Summary

UGS v0.2 defines a portable, Git-native change-governance baseline. It makes
the change unit, commit metadata, review evidence, protected-branch flow,
release object, and minimum enforcement surface explicit without depending on
one hosting platform.

This repository applies that baseline to itself. The repository policy,
managed hooks, GitHub mapping, equivalent CR archive, trusted signer registry,
and reusable validators are included in the v0.2 baseline.

## Included capabilities

- `continuous` branch profile with one protected long-lived `main` branch.
- `rebase-ff` as the declared integration strategy.
- Topic-branch and patch-series change model with the UGS CR field set.
- Conventional commit types, trailer-based metadata, and history-rewrite
  boundaries.
- Change-level review policy with explicit test evidence and sensitive-path
  maintainer acknowledgment.
- Signed annotated release-tag requirements.
- High-trust SSH-signed commit verification using the repository signer and
  revocation files.
- Managed `commit-msg` and `pre-push` hooks plus GitHub Actions validation.
- Archive-friendly CR records under `cr/` for non-GitHub integration paths.

The six archived change requests (`CR-0001` through `CR-0006`) document the
incremental adoption of these capabilities.

## Compatibility and trust boundaries

This release does not remove any v0.2 public document path or change the
meaning of the UGS Core v0.2 normative rules. The small additions in this
packet are repository-local release bookkeeping. The repository's stricter
local contract is intentional: commits proposed for integration must use a
trusted SSH signature, while historical commits before the signing adoption
remain preserved for traceability outside that high-trust claim.

The governance conformance claim starts with the first non-bootstrap change
after adoption
(`93b54733e794037fc5fe9d161efe0d654085e66d`). The high-trust signing claim
starts with the signing-enforcement change
(`5cc6c9344b657354f463cf06fbb7d38f964a9c6d`). Keep these anchors stable when
preparing the release; verification should use the full object IDs.

## Verification

Run the following checks from the repository root before publishing the tag:

```bash
scripts/validate_repo.sh
scripts/validate_commit_range.sh 5cc6c9344b657354f463cf06fbb7d38f964a9c6d^..HEAD
scripts/validate_commit_signatures.sh 5cc6c9344b657354f463cf06fbb7d38f964a9c6d^..HEAD
for file in cr/CR-*.md; do scripts/validate_cr_record.sh "$file"; done
bash -n .githooks/* scripts/*.sh
```

The release object must be a signed annotated tag. Downstream consumers can
verify it with the commands in [`RELEASE.md`](../RELEASE.md).

If the release key is new, add its public key to `keys/allowed_signers` through
a separate signed CR before creating the tag. Record the key's role and any
rotation or revocation context in that CR; never place private key material in
the repository.

## Deferred to v0.3

The following are intentionally planning items rather than v0.2 requirements:

- a canonical machine-readable policy manifest and schema;
- strict, OID-bound CR and review records;
- remote validation for every ref and release-tag immutability;
- signer roles, rotation metadata, and signed review attestations;
- portable conformance fixtures and a reference CLI;
- optional repository-quality and supply-chain profiles.

The proposed scope and migration order are recorded in
[`docs/roadmap/v0.3.md`](../docs/roadmap/v0.3.md).

## Publication checklist

The release is publishable only after a maintainer has:

1. selected the exact target commit;
2. confirmed a clean working tree and successful verification above;
3. created a signed annotated tag named `v0.2.0` with a trusted release key;
4. verified the tag locally; and
5. pushed the tag without updating or replacing an existing release tag.

Until those steps are complete, this file is a release packet, not a claim
that the public tag already exists.

## Rollback

Because v0.2 is documentation and governance data, rollback is performed by
reverting the release-packet change through a new signed CR. A published
release tag must never be rewritten; if a published release is defective,
publish a superseding patch release with corrected notes and verification
guidance.
