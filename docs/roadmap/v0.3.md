# UGS v0.3 Roadmap

**Status:** historical planning document; the v0.3 policy and conformance
profile was adopted by CR-0021. Remaining roadmap items are post-adoption
profiles and optional capabilities.
**Baseline:** [UGS v0.2.0 release packet](../../releases/v0.2.0.md)

## 1. Intent

UGS v0.2 establishes a clear Git-native governance model. v0.3 should make
that model interoperable: two independent implementations should be able to
read the same repository declaration, validate the same change request, and
produce materially equivalent conformance results without relying on a
particular hosting platform.

The goal is not to turn UGS into a hosting service or a project-specific build
system. The goal is a small, versioned protocol with a human-readable
specification and a testable machine interface.

## 2. Design principles

1. **One semantic source.** A machine-readable declaration is authoritative;
   prose documents explain and render it rather than silently redefining it.
2. **Git-native evidence.** Refs, commits, tags, trailers, patch series, and
   signed objects remain the portable evidence layer.
3. **Local/remote parity.** Hooks provide fast feedback, while server or CI
   adapters provide the non-bypassable enforcement boundary.
4. **Append-only auditability.** CR decisions, exceptions, signer changes, and
   release identities must be traceable without mutable platform UI state.
5. **Capability over guesswork.** A repository declares which review, signing,
   release, and automation capabilities it actually provides.
6. **Safe migration.** Existing compliant v0.2 history is not retroactively
   invalidated by a v0.3 implementation upgrade.

UGS remains in a rapid-iteration phase before v1.0. Version 0.x releases do
not promise compatibility across manifest fields, schemas, commands, reports,
or validator behavior. Each change must instead document its migration impact,
rollback path, and any intentional invalidation of draft material.

## 3. Proposed repository surface

CR-0010 selected JSON for the initial draft and CR-0021 adopted the resulting
policy and conformance profile. The v0.3 profile is now documented in
`docs/git/ugs-v0.3-profile.md`; `REPOSITORY_POLICY.md` remains read in parallel
for migration comparison and warning reporting.

```text
.ugs/
  policy.json             canonical repository declaration
  schema/                 policy, CR, trailer, signer schemas
  conformance/            portable positive and negative fixtures
  migrations/             version transition notes
docs/git/                 normative, human-readable specification
docs/roadmap/             non-normative plans (this document)
cr/                       strict, append-only equivalent CR records
keys/                     trust files plus identity/rotation metadata
releases/                 release notes and verification material
scripts/                  reference validators and server adapters
tests/fixtures/           cross-implementation test vectors
```

UGS should not require application directories such as `src/` or `lib/`.
Those belong to the repository's language and product profile. UGS should
instead require that project-specific entry points and evidence be declared
and discoverable.

## 4. Workstreams and acceptance criteria

### P0 — Canonical declaration and vocabulary

- Define a versioned `.ugs/policy.json` format and schema.
- Normalize field names currently expressed in multiple ways (for example,
  signing level, review model, and review-conclusion storage).
- Declare protected refs, merge strategy, branch profile, commit types,
  required checks, release rules, and exception capabilities in one place.
- Define unknown-field, extension, and schema-version behavior.

**Exit criterion:** a clean checkout can be validated from the manifest alone,
and contradictory prose declarations fail conformance checks.

### P0 — Conformance command and fixtures

- Publish a reference command such as `ugs check` (a shell implementation is
  acceptable initially).
- Add positive and negative fixtures for commit messages, trailers, CRs,
  signatures, tags, and branch transitions.
- Emit both human-readable output and a stable machine-readable report.
- Test the validators in disposable bare repositories, not only against the
  UGS repository itself.

**Exit criterion:** two implementations agree on the result for the published
fixture set, including failure reasons.

### P0 — Remote and release enforcement

- Provide GitHub and bare-Git adapters for the same policy checks.
- Validate all relevant refs, including `v*` tags; require annotated,
  trusted, correctly named release tags that point to commits.
- Reject release-tag deletion or replacement and document the server-side
  capability required for that guarantee.
- Pin third-party actions and use least-privilege workflow permissions.

**Exit criterion:** bypassing a local hook does not bypass protected-branch or
release invariants at the authoritative enforcement boundary.

### P1 — CR, review, and provenance model

- Define a strict CR schema with unique ID, revision, status, decision, exact
  base/head OIDs or range, policy version, and integrated result.
- Replace substring matching with normalized object/ref comparisons.
- Define how review conclusions survive rebase, squash, merge commits, and
  patch-series regeneration.
- Distinguish author claims from reviewer attestations; specify whether
  attestations must themselves be signed.

The base/integrated-result reachability rule and strategy-specific identity
rules are implemented by the v0.3 CR validator and its disposable fixtures;
review-attestation inheritance is implemented for trailer evidence; signed
reviewer attestations remain follow-up work.

**Exit criterion:** an archived CR can be matched to exactly one integrated
  result and independently audited after a hosting platform is unavailable.

### P1 — Profiles and exception lifecycle

- Publish a profile × merge-strategy compatibility matrix, including `squash`.
- Define conformance levels such as `baseline`, `standard`, and
  `high-trust` without changing the meaning of the two existing branch
  profiles. These first two items are implemented in
  `docs/git/ugs-conformance-levels.md`.
- Make bootstrap and emergency paths one-time or time-bounded, authorized,
  and append-only recorded, with mandatory post-event review.
- Define signer identity roles, effective dates, rotation, revocation, and
  recovery semantics.

**Exit criterion:** every allowed exception and integration strategy has a
  deterministic evidence and recovery path.

### P2 — Optional quality and supply-chain profiles

- Specify optional repository-quality expectations (`LICENSE`, security
  contact, contribution conduct, support policy, and test entry points).
- Specify optional provenance expectations (dependency/action pinning, SBOM,
  reproducible artifacts, and release attestations).
- Add monorepo, submodule, generated-file, and large-file capability guidance
  without burdening the Git-native core.

**Exit criterion:** a repository can opt into stronger quality or supply-chain
  guarantees without changing the Core conformance contract.

## 5. v0.2 → v0.3 migration

Migration should happen in explicit stages:

1. **Inventory:** record the v0.2 profile, trusted-signing anchor, protected
   refs, and existing CR IDs.
2. **Dual-read period:** introduce the manifest and schemas while continuing to
   read the v0.2 text declaration; report mismatches as warnings first.
3. **Evidence upgrade:** retain old CR IDs and history, add full OIDs,
   revisions, and integrated-result fields to new or amended records.
4. **Enforcement opt-in:** enable strict manifest, tag, and CR checks per
   repository capability; publish the conformance report.
5. **Version transition:** only after fixtures and adapters are available,
   declare v0.3 as the active policy version and publish migration notes.

No migration step should reinterpret an already accepted v0.2 commit as
invalid solely because v0.3 adds a stronger check. A rule that would do so is
a compatibility change and must be called out as such in release notes.

## 6. Post-adoption work

- JSON, YAML, or another format for the canonical manifest.
- Whether CR records remain Markdown with front matter or move to a separate
  canonical data form with a rendered Markdown view.
- The minimum signature/attestation model for review conclusions.
- Server capability levels and the portable fallback when no server hook is
  available.
- Whether conformance levels are part of Core or a companion profile.
- The point at which UGS moves from rapid 0.x iteration to a 1.0 stability
  contract.

These items are follow-up profile work and are not requirements of the adopted
v0.3 policy and conformance profile.

## 7. Definition of done for v0.3

v0.3 is ready for adoption when a repository can:

- publish one canonical, versioned policy declaration;
- validate its declaration, CR, commits, signatures, and release tags with a
  reference implementation;
- produce a reproducible conformance report from a local clone;
- enforce the declared protected-ref and release invariants remotely where the
  repository claims that capability;
- migrate its v0.2 history without rewriting protected history; and
- explain all normative changes, compatibility effects, and rollback steps in
  release notes.

The conditions above describe the adoption gate recorded by CR-0021. This
roadmap remains non-normative for post-adoption profiles and future work.
