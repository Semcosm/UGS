# UGS Long-Term Roadmap: v0.4 to v1.0 and Beyond

**Status:** non-normative planning document

**Planning baseline:** UGS v0.3.28, with the active high-trust conformance
level, continuous branch profile, rebase-ff integration, and the optional
quality, supply-chain, and repository-shape profiles.

This roadmap turns the post-adoption items in the [v0.3 roadmap](v0.3.md)
into a staged plan. It is a planning aid, not a new conformance requirement.
Any normative change must be proposed through a change request, pass the
applicable fixtures and validators, and ship with a migration and rollback
note. Dates are indicative; exit criteria are the durable commitments.

## 1. Direction

UGS should mature from a well-tested reference repository into a small,
interoperable protocol that independent implementations can adopt without
depending on GitHub or on the UGS source tree. The long-term target is a
stable Core with separately versioned profiles and adapters:

- **Core:** Git objects, policy declarations, change requests, review evidence,
  signatures, protected refs, and release identity.
- **Profiles:** optional quality, supply-chain, repository-shape, and future
  domain capabilities with explicit evidence contracts.
- **Adapters:** hosting, CI, server-side receive, and local tooling mappings
  that do not redefine Core semantics.
- **Reference tools:** validators, fixture runners, migration helpers, and
  deterministic reports that make the protocol executable offline.

The project should optimize for auditability, portability, and gradual
adoption. It should not become a hosting service, a universal build system, or
an opaque certification authority.

## 2. Current baseline and gaps

The v0.3 line already provides a canonical JSON policy, a CR record format,
conformance levels, profile validators, signed release checks, bootstrap and
upgrade tooling, disposable Git fixtures, and a generated document map. The
following gaps still prevent a long-lived compatibility contract:

1. **Wire-format stability:** policy and CR schemas have no published
   negotiation or deprecation process, and machine-readable failure codes are
   not yet a cross-implementation contract.
2. **Evidence interoperability:** reviewer and test attestations, rebase and
   squash provenance, and the cross-binding of those attestations to CR and
   release evidence still need a portable contract. CR-0074 now defines the
   canonical CR projection and binding itself.
3. **Capability discovery:** an adapter can report checks, but the protocol does
   not yet describe server enforcement strength or a portable fallback when no
   authoritative receive hook exists.
4. **Operational lifecycle:** signer rotation, compromise recovery, profile
   deprecation, and long-lived consumer upgrades need documented, tested
   procedures rather than repository-specific conventions.
5. **Ecosystem confidence:** the fixture corpus has independent Bash/Python
   implementations, but there is no repeatable process for third-party
   implementations to publish conformance results.

These gaps are sequencing constraints for v1.0. They are not reasons to widen
the Core with platform-specific features.

## 3. Staged plan

### Phase A - v0.4 contract hardening (near term)

Target window: the next minor series after v0.3. The focus is making current
behavior predictable before adding new semantics.

Deliverables:

- Publish a canonical vocabulary table and compatibility aliases for terms that
  currently differ across Core prose and machine validators, including
  `release-line`/`release` and `merge-commit`/`merge`. Record the canonical
  spelling, accepted legacy input, and the release that may retire each alias.
- Publish a policy and schema compatibility guide covering unknown fields,
  extension keys, schema-version negotiation, deprecation, and downgrade
  behavior.
- Document the boundary between the protocol's `policy_version` and the
  distribution's SemVer: a patch release may correct implementation or prose
  without changing the policy wire contract, while a policy-version change
  requires migration notes and compatibility evidence.
- Define stable error identifiers and a normalized JSON report for every Core
  validator; preserve human-readable diagnostics as a presentation layer.
- Add fixture vectors for malformed manifests, all merge strategies, OID and
  ancestry edge cases, signer rotation, tag replacement, and bootstrap
  rollback.
- Provide an offline migration command that inventories a repository, previews
  changes, writes a recoverable backup, and emits a post-migration report.
- Expand release and workflow checks to verify action pinning and evidence
  paths where a profile declares them.
- Audit historical CR records whose status and integrated-result fields do not
  agree; complete immutable evidence where possible, or record an explicit
  grandfathered exception with its reason and audit scope.
- Keep the generated document map and bootstrap component inventory as release
  gates so documentation and distribution cannot silently drift.

Exit criteria:

- The Bash and Python implementations produce equivalent pass/fail decisions,
  error identifiers, and normalized report fields for the published corpus.
- The canonical vocabulary and alias behavior are enforced consistently by the
  schema, shell validator, Python checker, and fixture corpus.
- A v0.3 consumer can run a dry-run migration and roll back without changing
  its protected history.
- Every accepted CR is either bound to an integrated result or explicitly
  classified as grandfathered; a pending field is not silently treated as
  accepted evidence.
- Every new policy or schema field has a documented compatibility class and
  an unknown-field rule.

### Phase B - v0.5 interoperability and evidence (medium term)

Target window: after contract hardening. The focus is preserving review and
provenance when the hosting platform or integration shape changes.

Deliverables:

- **Delivered by CR-0074:** adopt a canonical CR data model whose sole
  persistent authority is flat Markdown, with lossless rendering plus a
  deterministic JSON projection and binding across CR revision, source range,
  integration object, and final result. Legacy v0 records remain historical
  evidence and are not rewritten by this contract.
- Specify signed reviewer and test attestations, including identity roles,
  namespaces, validity periods, revocation, and the behavior after rebase,
  merge, or squash.
- Define an adapter capability document that states which checks are local, CI-
  enforced, receive-enforced, or merely advisory.
- Add portable receive-side guidance for bare Git and a clearly documented
  degraded mode when the authoritative server capability is unavailable.
- Complete signer lifecycle procedures for planned rotation, emergency
  recovery, revocation, and post-event review, with disposable fixtures.
- Publish profile versions independently from Core and test mixed-version
  repositories during upgrade and rollback.

Exit criteria:

- An archived CR and its attestations can be audited from Git objects and
  repository-relative evidence after the original hosting service is gone.
- At least two independent implementations consume the canonical CR and
  fixture corpus and publish reproducible conformance results.
- An adapter can state its enforcement boundary and a consumer can detect a
  downgrade from authoritative to advisory checks.

### Phase C - v0.6 supply-chain and operations (medium to long term)

Target window: after the evidence model is stable. The focus is moving the
optional declared profiles toward verifiable production evidence.

Deliverables:

- Add profile fixtures that validate action pinning, SBOM completeness, build
  records, artifact digests, and signed release attestations together.
- Define offline verification and mirror/air-gap procedures for release
  evidence, including retention and recovery of signing material.
- Document a key-transparency or equivalent audit trail for signer additions,
  rotations, and revocations without requiring a hosted service.
- Exercise disaster recovery for bootstrap archives, policy backups, and
  trusted-signer registries in disposable repositories.

Exit criteria:

- A standard or high-trust supply-chain claim can be checked from a release
  packet and repository-local evidence without network access.
- Evidence and signer lifecycle tests cover both normal rotation and compromise
  recovery, with immutable post-event records.

### Phase D - v0.7 adapter and repository ecosystem (long term)

Target window: after Core evidence and operation contracts are stable. The
focus is broad adoption without changing the mandatory Git-native baseline.

Deliverables:

- Version the adapter contract and publish capability and degraded-mode
  semantics for bare Git, GitHub, GitLab, Gerrit, and CI-only deployments.
- Add adapter conformance fixtures that distinguish local, CI, receive-side,
  and advisory checks.
- Extend repository-shape guidance for monorepos, submodules, generated files,
  large files, and artifact promotion while keeping each capability opt-in.
- Publish policy composition guidance for organizations that govern multiple
  repositories without making a central service part of Core.

Exit criteria:

- Each supported adapter can publish a reproducible capability report and
  identify checks that are unavailable in its deployment.
- At least one non-GitHub adapter passes the same Core fixture corpus and the
  repository-shape profiles have migration and rollback guidance.

### Phase E - v1.0 stability (long term)

Target window: when Phases A through D have met their exit criteria. v1.0 is a
compatibility milestone, not a feature-count milestone.

The v1.0 proposal should:

- freeze the Core vocabulary, policy wire format, CR binding rules, signature
  namespaces, report schema, and conformance result semantics;
- define a compatibility promise for patch and minor releases, including the
  supported migration window and a minimum deprecation period;
- publish a versioned Core test suite and a transparent process for third-party
  implementation claims;
- separate normative Core, optional profiles, and adapter specifications in
  release packets and document maps;
- define a security response process for validator defects, signer compromise,
  and evidence forgery, including a non-destructive superseding release path;
- provide a reference implementation matrix for local hooks, CI, bare-Git
  receive, and at least one hosting adapter; and
- publish a v1.0 migration guide that preserves accepted v0.x history and
  explains every intentional tightening.

v1.0 should not make a repository claim stronger guarantees merely by changing
its version string. A conformance claim must continue to name the Core version,
profile versions, evidence level, and enforcement boundary.

### Phase F - post-v1.0 ecosystem

After the Core contract is stable, work can extend coverage without expanding
the mandatory baseline:

- policy discovery and verification for air-gapped and mirrored repositories;
- richer build provenance and reproducible-build attestations;
- monorepo ownership and component-level policy boundaries;
- bindings or libraries for commonly used languages, generated from the same
  schemas and fixture corpus; and
- adapter conformance claims backed by published evidence rather than a central
  certification service.

Each capability should remain opt-in until its evidence model, migration path,
and independent implementation story are complete.

## 4. Cross-cutting workstreams

The phases above are sequenced, but these workstreams run throughout them:

| Workstream | Near-term measure | v1.0 outcome |
| --- | --- | --- |
| Specification | Every normative rule has one source and a schema or fixture | Core semantics are frozen and versioned |
| Interoperability | Bash/Python parity and stable error identifiers | Two or more independent implementations pass the same corpus |
| Security | Key rotation, revocation, and evidence-binding fixtures | Published incident and recovery process |
| Operations | Dry-run, backup, rollback, and idempotence checks | Supported migration window for v0.x consumers |
| Adapters | Explicit enforcement-boundary reports | Versioned adapter contracts with degraded-mode behavior |
| Documentation | Generated map, release packet, and migration notes are gates | Core, profiles, and adapters are navigable and separately versioned |

Progress should be reviewed at each release packet using these measures rather
than by counting scripts or documents.

## 5. Release and decision gates

Before adopting a new normative capability, the maintainer group should record
the following in a CR:

1. the problem and affected Core/profile boundary;
2. the schema, fixture, validator, and adapter changes;
3. compatibility class, migration preview, and rollback procedure;
4. security and signer impact;
5. independent implementation or review evidence; and
6. the release packet and document-map updates.

The release packet should identify any fields or checks entering deprecation,
the last release expected to accept them, and the first release that may reject
them. Emergency exceptions remain append-only records and do not bypass the
same post-event review.

## 6. Open decisions

CR-0074 resolves the CR representation decision: v1 CR data is stored as flat
Markdown without front matter or a JSON sidecar; the reference parser produces
the deterministic projection and `ugs-cr-binding/v1` binding, while legacy v0
records remain grandfathered historical evidence.

The following decisions remain before the v1.0 freeze:

- Which signature format and trust roots are portable enough for reviewer
  attestations across SSH, OpenPGP, and future signing systems?
- Which adapter capabilities can be verified from Git evidence, and which must
  remain explicitly reported external assertions?
- What is the minimum supported migration window for a v1.x consumer, and how
  are profile versions negotiated when a repository contains mixed components?
- Which conformance results may be published as a claim, and what evidence must
  accompany that claim without creating a central certification dependency?

Decisions should be made with fixtures and prototype implementations before
they are added to the v1.0 normative contract.

## 7. Success criteria

UGS is ready for a stable v1.0 claim when a new implementation can, from the
published specification and fixture corpus alone:

- read a policy and determine its Core and profile versions;
- validate a CR, its review and test evidence, and its integrated result;
- verify release identity and declared supply-chain evidence;
- produce the same normalized result as the reference implementation;
- explain the enforcement boundary of its adapters; and
- migrate a supported v0.x repository with a preview and recoverable rollback.

Until then, v0.x releases should continue to state that schemas, commands,
reports, and validator behavior may change, with the migration and rollback
impact documented in each release packet.
